# Spike 2026-11-20: techniques for a 28-call, 8-minute, 32k-context SWE agent

Web search only, public literature. **I read no paper in full.** Every number below is from a search snippet or one
fetched blog page; check before citing. Not repeated here: the topics in [literature.md](literature.md) and
[papers.md](papers.md) (hashline, verifiers, turn limits, Gemma template bug, trajectory SFT in general).

## Two framing points

- Most "budget" papers (turn caps, early termination, trajectory reduction) save cost. **Our score has no cost term.**
  Only the part that forces an edit before call 28 matters to us. Do not copy their cost wins.
- Most evidence is on frontier models. Small-model evidence is thin and mostly vendor or blog.

## Ranking

### 31B main entry

| Rank | Technique | One-line test plan |
|---|---|---|
| 1 | #1 Budget checkpoints, paired with #6's fixed sequence (edit by about call 10) | One prompt change; two 31B replicates on 36 tasks; judge on median first-edit call (baseline 11-14, need -3) and on budget stops not rising; resolution only as a side note |
| 2 | #2 Loop guard, plus #3 only if a log check shows context pressure | First grep the existing 31B logs for identical consecutive calls and prompt-token peaks; build the prompt only if over 10% of runs show either |
| 3 | #7 Pre-submit diff review (weak evidence, cheap) | Run on the multi-hunk subset of dev tasks; keep only if a post-edit call changes the patch in a visible share of runs and resolution is not lower |

Reason for the order: 31B refuses only about 6% of edits (A44), so edit mechanics (#4) are not its limit. The visible
31B problem in our notes is the late first edit, and #1 is the only technique with a direct mechanism for it.
**Honest odds: all three are likely worth 0 to 3 points, below what 36 tasks can see.** The paper-quality evidence
that any of them helps an untrained model on SWE tasks is thin.

### E4B bonus entry

| Rank | Technique | One-line test plan |
|---|---|---|
| 1 | #4 Near-miss feedback on a refused edit (tool-side if we own `edit_file`; else the verbatim-copy prompt) | One E4B replicate (about 0.5 USD or local GPU); success = edit refusal rate down from 39% and retries per refusal down; resolution is noise at 8-9 points |
| 2 | #5 Text-block action protocol, only after confirming ADK can host it | 1 hour to read how the YAML maps tools; if it cannot, drop it and spend the time on #2 for E4B |

Not recommended in the 5-day window: #9 and #10 (the only options with published large gains, 20 to 40 points, but
they need thousands of filtered trajectories from a strong teacher, and we have about 56 resolved runs over 17 tasks
and no GPU budget).

## Caveats

- Several "results" above came back through a search summariser, not the paper. The two I would check first before
  relying on them: the SWE-smith step-limit share (53%) and the Complexity Trap token share (84%).
- The ai-muninn numbers are one blog, one author, one scaffold; the E4B 16.67% is on SWE-bench Lite with a
  hundred-step budget, not comparable to our 28 calls.
- No source found tests any of #1, #2, #3 or #7 on a Gemma-class model under a 28-call limit.

## Follow-up from our own data (2026-11-20)

- **#1 has support in our logs (A47):** in four 31B runs, first edit before call 10 resolved 40 of 60 (67%), later 16 of 84
  (19%). That is a correlation (easy tasks edit early), and A47 found a call cap would cost resolutions. A prompt that
  asks for an early edit is different from a cap, but it is the test to run, with first-edit call as the signal.
- **#4 is mostly done for E4B:** the edit skill (`e4b_edit2`) returns the closest lines on a failed match and cut refusals
  from 38 to 50% to 19 to 26% (A58) with no gain in resolution. More refusal work will not move the score.
- **#2 and #3 cannot be checked yet:** the 31B logs (`dev-a0`, `dev-a2`) are not restored in `data/runs` (GEM-94).
- **Blocked on Kaggle GPU quota:** every 31B test above needs two L4x4 replicates (about 2.9 h each).
